# Going live

Everything below needs keys, a funded Bradbury account, and the official
`genlayer` CLI. Network and keychain access are required for live operations.
Do not submit transactions before the offline suite is green.

## 0. Prove it runs before touching the chain

```bash
make check
make dry
```

 assertions, no chain, no network. `make dry` then walks all four scenarios
end to end against the stub, so the exact sequence you are about to send has
already been run somewhere. If this is red, stop. Nothing further will
tell you anything true.

The suite has been mutation-checked: breaking any of the fail-closed rules, the
settlement table, the gate, or the dedup key makes it go red. That is the reason
to trust it, not the count.

What the stub cannot fake is the one thing that matters most here: validator
disagreement. Every claim about decidability and about the defence has to come
from Bradbury receipts, never from this suite.

Every write is generated by `scripts/gl_cmd.py`, which escapes the arguments and
prints the manifest line to append. Hand-quoting a body with an apostrophe or a
zero-width character into a shell is how a delivery gets corrupted before it is
ever judged.

## 1. Deploy

```bash
python3 scripts/build_deploy.py
genlayer deploy --contract contracts/retainer.deploy.py
export CONTRACT=0x...
```

The full documented source exceeded Bradbury's transaction gas ceiling on the
first live attempt. `build_deploy.py` removes comments and docstrings and checks
that the executable AST is unchanged. It preserves every prompt and the SDK
dependency line; the generated source is committed for verification.

The `Depends` line at the top of the contract pins the same SDK build that
Jastrow and Suborn are deployed against. Do not bump it during the build window.

## 2. Open the reference brief

`calibration/reference-brief.json` deliberately uses the same campaign rule that
Jastrow and Suborn were measured on, so that the three sets of receipts describe
one object instead of three unrelated ones.

The gate runs inside `open_brief`. Three outcomes are all worth a receipt:

| gate says | what happens | what it demonstrates |
| --- | --- | --- |
| `DECIDABLE` | brief opens, fee escrowed | the normal path |
| `AMBIGUOUS` / `UNDECIDABLE` | brief stored `REJECTED`, fee returned | a job that never opened |
| validators split | transaction ends `UNDETERMINED` | the Jastrow finding, in receipt status |

The third is not a failure to work around. It is the measurement, and Jastrow's
own live report already returns `UNDECIDABLE` on its own reference spec. Publish
whichever of the three actually happens, in those words.

## 3. Run the four scenarios

Open a separate brief for each, so each has its own receipt chain.

| # | brief | delivery | expected |
| --- | --- | --- | --- |
| 1 | reference spec | `examples/01-honest-pass.json` | `PASS`, fee to the agent |
| 2 | reference spec | `examples/02-spec-fail.json` | `FAIL`, stake slashed |
| 3 | reference spec | `examples/03-forged-pass.json` | judge flips, defence catches it, `UNVERIFIABLE` if the judge is actually fooled |
| 4 | a spec written vaguely on purpose | none | the brief never opens |

Scenario 3 is the one to spend time on. A judge that is not actually fooled by
the forged deliverable produces a `PASS` that the defence agrees with, and that
proves nothing at all. If the live judge holds, say so and publish the round
count, rather than reporting a defence that was never tested. Suborn's rule
applies unchanged: a class that did not reach the round threshold is
inconclusive, not a win.

Scenario 4 needs a brief nobody would call answerable. Something like "the
deliverable should be good quality and roughly on time" is the honest kind of
vague, not a trick input.

## 3a. Let the agent do scenario 1

Scenario 1 is worth more when the agent takes the brief rather than a person
running `gl_cmd.py` by hand, because the track is about agents and the contract
alone does not show one.

```bash
python3 agent/retainer_agent.py --address $CONTRACT --dry
python3 agent/retainer_agent.py --address $CONTRACT --settle --manifest runs/bradbury.jsonl
```

The dry pass prints a decision and a reason for every brief, including the ones
it declines. Run it against the scenario-4 brief too: an agent that visibly
walks away from a job with an unanswerable spec makes the gate's point better
than the receipt does.

The agent writes its own manifest lines as it goes, so `collect_receipts.py`
picks its transactions up with everyone else's.

## 4. Diagnose missing transactions from the start

In the Suborn run, six submitted transactions never produced a state record, and
RPC diagnosis could not establish whether they were rejected or simply not
found. Do not wait for that to happen again:

- record the transaction hash the moment the CLI prints it, before waiting for
  any receipt
- keep the submit manifest separate from the collected receipts, so an
  unconfirmed transaction is visibly unconfirmed rather than absent
- treat "no state record" as its own outcome in the report, not as a gap

`scripts/collect_receipts.py` and `scripts/diagnose_missing.py` are already
ported from Suborn `9c7b0af`, with the chain I/O and the `genlayer call` output
parser unchanged. `scripts/gl_cmd.py` prints the manifest line to record for
every write, so there is nothing to remember under pressure.

## 5. What must be true before anything is published

- every number on the page traces to a Bradbury receipt with a real validator
  address and a real cost in GEN
- no simulated or fixture data is presented as a measurement, anywhere
- the page says the gate and the defence run inside Retainer, and that the
  Jastrow and Suborn receipts are linked evidence, not cross-contract calls
- the "44 attacks across 10 classes" claim is attached to the judging prompt,
  which is copied byte for byte from Suborn `9c7b0af`, and not to the referee
  framings, which are adapted and need their own live numbers
- any scenario that did not reach its round count is labelled inconclusive

## Live-run compatibility checks

The live run exposed two differences the original stub had hidden: this pinned
SDK has no `Address.ZERO`, and `Address(existing_address)` is not a valid copy
constructor. Use the explicit zero-address string and pass the existing sender
address directly to the EVM recipient interface. `test/test_sdk_compat.py`
checks both cases, including the EVM withdrawal branch.

A transaction status of `ACCEPTED` alone does not establish successful
execution. Check `execution_result == FINISHED_WITH_RETURN` before issuing a
dependent write. The agent now waits after saving each manifest entry.
External value transfers execute on finalization; an accepted withdrawal
is not yet proof that the recipient received funds.

Prior deployments and failed transactions remain under `runs/initial-sdk-error/`
and `runs/withdraw-sdk-error/`. The current deployment is recorded in
`runs/deployment.json`; do not mix contract state across these runs.
